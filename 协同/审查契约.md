# 接力审查契约（工程审查 MA-02 v0.3，含与思维评审共用的上限）

- **这是接力审核条款的唯一语义源头**：审几轮、问题台账、四种出口、回信末四行、到顶交常浩、续审授权、哪些不算 L0，只在这里写。别处（《工程流程》第 8 节第 3 条、my-skills thinking-review `references/relay.md`、digital-twin DT-ORC ARCHITECTURE、各项目 AGENTS）只留指针，不复述；要改规则只改这里。
- **分工**：本契约写语义和边界；驿窗怎么机械执行（计数、核对版本、拒收、停下、通知、回信存档、记录保留多少张）以 postpane [`docs/chatgpt-channel.md`](https://github.com/Natsukashii1997/postpane/blob/main/docs/chatgpt-channel.md)「审核门」一节为准。两边对不上时先停下报告，不自己选一边。
- **思维评审**怎么判、怎么出口归 my-skills `thinking-review`；它只和本契约共用第 5.5 节的上限与机械控制。
- 来源：2026-11-27 从 multi-agent `modes/MA-02-engineering-review.md` 第 1～5、8、9 节和 `MA-01-thinking-review.md` 第 6 节「共用上限」一段并入（agent-kit 深度梳理方案第三项，常浩 2026-11-26 批「只留一份协同契约」、2026-11-27 定放 agent-kit），语义没改。沿革见第 8 节。

## 1. 目标

让实现者以外的一方判断「这次改动能不能被接受」：发现作者漏掉的逻辑、边界和回归风险，并且**在问题解决时结束**，不无限往返。要消除的单 Agent 风险：作者盲区；以及工程接力的两种老毛病：审到第 5 轮还在原地打转、拆单续审绕开计数。

审查是否完成由 ChatGPT 判断；审查事实由持久的问题台账承载；能不能继续自动往返由驿窗按硬规则执行。上限（默认 5 轮，可调 1–9）内每一轮有价值就继续，没价值就停，到上限仍不通过必须交还常浩。

## 2. 适用 / 禁用

- 适用：L1 及以上的代码、脚本、配置改动，以及不算 L0 的规则文档改动（如写进架构基线的执行身份、授权、合并规则），已有 PR 和自测证据。规则文档改动里，要定方向、改前提的先走思维评审（见下条），方向已定、审的是写法和前后一致的走本契约。
- 禁用：
  - L0 不送审，只做机械检查。L0 指《工程流程》第 3 节可直接进 main 的纯文档、记账类改动；**写进架构基线的执行身份、授权、合并规则不算 L0**；
  - 方向问题（问题定义、路线、架构前提）→ 转思维评审（my-skills `thinking-review`）；
  - 只缺可运行证据、不缺判断 → 先补测试（或等独立验证模式 MA-03 成立后转它，见 [routing.md](routing.md)），不靠多审一轮补证据。
- 与 MA-03（候选）的分界：工程审查回答「能不能接受」，产出审查意见和接受/升级决定；MA-03 回答「关键行为有没有被独立证实」，产出可复现的运行证据。工程审查可以调用独立验证作为证据，但不默认绑定 Codex。
- 思维评审只共用第 5.5 节的上限与机械控制（上限、两种计数、格式补一次、通过通知），不套用问题台账和 P0/P1，出口仍按 thinking-review。

## 3. 角色

| 协作角色 | 默认承担 | 说明 |
|---|---|---|
| Owner | 常浩 | 合并授权、到顶后的去向、决策升级、L3 的动作授权 |
| Builder | Claude Code（Codex 会话也能经驿窗发起送审，postpane#280、#282） | 实现、自测、返修；对台账只能**提议**关闭、改级、转单 |
| Challenger | ChatGPT High（经驿窗） | 独立工程审查；判断审查是否完成、下一轮有没有价值；**确认**台账状态变化。默认依据送审包和 PR 判断，能否读仓库、跑命令取决于当次连接的工具，不写死 |
| Verifier | Claude 自测；L3 需要时加独立验证方 | 自测不算独立验证 |
| Coordinator | 驿窗执行硬规则；Claude 记运行记录；Hermes 派单的任务由 Hermes 记录状态 | 驿窗不判断语义；Hermes 不出技术「通过」 |

谁能当独立验证方、各 Agent 的长期档案和当下可用性，见 [agent-profile.md](agent-profile.md)。

## 4. 输入与交接物（接口）

- 送审前先定风险级（L0–L3，定义沿用 DT-ORC ARCHITECTURE 的风险分级），写进送审包第一行，并在调用 `relay_to_chatgpt` 时填 `risk`（L1–L3；L0 驿窗拒收）。风险级决定审查要求（第 5.1 节），不再决定轮数。
- 送审包：驿窗「六项」，即任务名与目标、改了什么和为什么、分支与 PR 链接、diff 或摘要、希望重点看哪里、按严重程度列问题。另外要绑定 `repo / base_sha / head_sha`；被审的 PR 链接要是送审包里第一个出现的 PR 链接。PR 只是交付对象，不是审查链身份：续审（含拆单、换 PR、换会话）要写审查链标识（调用时填 `chain`）、原验收目标、已累计轮数和未关闭台账（第 5.4 节）。有 PR 的送审必须带受审提交的完整 40 位 SHA（调用时填 `head`，不填时驿窗从送审包里写 head 的那一行认），否则驿窗拒收。
- 驿窗在送出前还会拒收：这条审查链上一张接力还在等 ChatGPT 回信（等它回信计入轮数后再送，或由常浩先结束那张）；填的 `chain` 驿窗没有记录。驿窗往已有审核的会话里送的话，第一行会自动加「【驿窗送审 请求号】」、末尾附轮次和上一轮台账，Claude 不用自己写。
- 第 2 轮起，送审包还要有：**本轮目的**（这轮修了什么、改了什么、要验证什么）、**上一轮台账**（驿窗带入，Claude 逐条写处理：已修并附证据 / 提议判定不成立并附反证 / 提议转单）。
- 回信：按严重程度（P0–P3）列问题，并给出更新后的问题台账（第 5.2 节）。P0/P1 必须写失败路径、违反的约束或风险依据；写不出的按 P2 及以下处理。回信最后四行：

  ```
  受审版本：<实际审过的 commit SHA>
  未决：P0 n，P1 n
  审查出口：通过 / 返修 / 证据不足暂停 / 决策升级
  结论：通过 / 需修改
  ```

  - 审查出口四档（第 5.3 节）；「通过」配「结论：通过」，其余配「结论：需修改」。驿窗结论仍是二态，四档写在倒数第二行。
  - 「未决」只用于展示和统计，不控制停机；写了「未决 0」也不能代替审查出口。
  - 版本锚点：「通过」只对实际审过的那个 commit 有效。回信写了「通过」时，驿窗核对：受审版本和送审的 `head` 对得上，PR 当前 HEAD 也没变（驿窗只核 head，base 等其他项由 ChatGPT 按项目契约审）。下面三种不放行，这一轮照样计数，旧结论不能用于新版本，但用当前 HEAD 重送就能解决，所以驿窗把回信转回、请 Claude 用当前 HEAD 重新送审，自动往返不停：受审版本对不上；PR 已有新提交（常见，每轮都会改交接文档）；升级前开的接力有 PR 却没记受审提交。驿窗读不到 PR 当前 HEAD，或这一轮送审没确认送到（见下条），才停下交常浩。到上限那一轮遇到版本问题，重送同样要常浩授权。说不清版本为什么对不上的，ChatGPT 应选决策升级。
  - 送达未确认：驿窗送出后没等到插件确认（超时，或确认前驿窗重启），就不知道 ChatGPT 审的是哪一版。这时自动往返停下交常浩；驿窗重启发现的、补格式请求发不出去的，按出错通知告诉发起会话一次「送达状态未知」（Claude 调用当场没送成的，调用返回里已经说了）。之后这张接力不再收别的话，同一段话重送不会重复发；它的回信到了只认那段话，照算一轮，但不放行通过；插件晚到的确认只在接力卡上补记一笔。直到下一轮送审确认送到，这层拦截才解除。没送成不算送达未确认（postpane#466，常浩 2026-11-20 定，只管会话发起的送审）：插件明确回报没点过发送，或发出时插件没连上、话没出驿窗的，这段话确定不在 ChatGPT 里，按没送成处理：接力和发送前一样，自动往返不停，调用返回里写明原因，同一段话可以直接重送、会真的再发一次。点了发送但没见开始、插件没说点没点过的，仍按送达未确认；驿窗自己发的补格式没送成，也照旧按送达未确认。
  - 末尾几行缺字段、值认不出、出口与结论对不上：驿窗先自动请 ChatGPT 只补一次格式（不计轮），还不对才把回信转回 Claude 并停下交还常浩。「未决」一行缺了不触发补格式。台账要写在「## 问题台账」标题下，驿窗才能原样带进下一轮。补格式只能补写末尾几行，不得改台账、实质判断或已写明的审查出口；出口与结论矛盾时以出口为准改结论；认不出出口时不能补出「通过」。

## 5. 审核门与停止条件（常浩 2026-11-14 裁决，取代 2026-11-07 的按级预算）

### 5.1 风险级只定审查要求

| 级别 | 送审 | 额外要求 |
|---|---|---|
| L0 | 不送审 | 机械检查 |
| L1 | 送审 | 自测和增量证据。只剩 P2/P3 时按「通过附建议」收口；有 P0/P1 时，改完必须复核一轮，不能「补改未复审」 |
| L2 | 送审 | 自测、回归与独立主审 |
| L3 | 送审 | 前置风险分析、必要的独立验证、常浩动作授权 |

所有级别共用同一个上限（第 5.5 节）；实际审几轮由第 5.3 节的审核门决定。

### 5.2 问题台账

- 每个问题一个永久编号（如 `P1-03`），改了严重程度也不换号。台账每轮随回信更新，驿窗保存每轮回信全文，并把上一轮台账带进下一轮送审；驿窗不理解内容，只保证记录不被悄悄改掉。编号稳定是便利，不是安全前提：每轮都要对账，漏掉的问题按未关闭处理。

| 状态 | 含义 | 解除阻断？ |
|---|---|---|
| 待修复 | 问题成立，还没修 | 否 |
| 待复核 | Claude 已返修并交了证据 | 否 |
| 已验证关闭 | ChatGPT 核实修复有效 | 是 |
| 判定不成立 | 有证据证明原判断误判或不适用 | 是 |
| 待决策 | 涉及设计取舍、风险接受、方案变更 | 否，走决策升级 |
| 范围外转单 | 确认和本次改动无关，已开 issue | 第 3 轮起的 P1 是；P0 任何时候都不是 |

- 谁能改状态：Claude 只能提议关闭、改级、转单，ChatGPT 确认后才生效；Claude 不能删问题。
- 范围内外由 ChatGPT 最后确认。第 3 轮起发现的范围外 P1 转单（开 issue）、不挡本单；范围内的 P1 即使是前几轮漏掉的，也照常挡。
- 「范围外转单」生效要同时满足：ChatGPT 确认与当前验收目标没有直接关系；issue 已实际创建成功，链接或编号写进台账，issue 里有问题描述和证据；台账保留原编号、严重程度、转出目标和转出记录。issue 没建成就不算转单，也不解除阻断。issue 是否存在、范围判断都由 ChatGPT 核，驿窗不核（常浩 2026-11-14 选的推荐做法）。

### 5.3 每一轮的目的与四种出口

- **第 1 轮：建立基线**。定受审范围和受审版本，列出阻断问题、非阻断建议和验证要求。
- **第 2 轮起：围绕没关闭的问题**。范围是原问题、返修 diff 及其直接影响的路径，以及原审查前提是否因改动失效。Claude 写本轮目的，ChatGPT 判断够不够、必要时调整范围。双方都能要求「这轮重新全面审」，但要说明实质变化（接口、设计、安全边界）。不预设每一轮做什么，问题都关闭了就提前结束。

| 审查出口 | 条件 | 驿窗怎么做 |
|---|---|---|
| 通过 | 本次范围内没有仍阻断的 P0/P1；历史阻断问题都有最终处置；返修没带出新的阻断问题；P2/P3 都有处理结果（已修、接受待后续处理、附理由不采纳、登记独立 issue 之一，不要求都修完）；审过的就是当前版本 | 结束，**通知常浩**（不用他确认）。通过后 Claude 合并前顺手改掉的 P2/P3 算「补改未复审」，在 PR 上写明，不再送审 |
| 返修 | 还有阻断问题，**而且下一轮有明确的、和上一轮不同的、能改变判断的工作**（有可行的修法、有新的验证价值）。同一问题上次修失败，说清为什么失败、换了修法，可以再来一轮；同样的思路再补一次不行 | 未到上限：转回 Claude 返修；到上限：见 5.5 |
| 证据不足暂停 | 有问题但缺关键验证材料 | 转回 Claude 并停自动往返；补齐后再送就续上。**这一轮照样计数** |
| 决策升级 | 要改已批准的需求、验收标准或关键安全假设；要接受风险；或已没有可信的修法 | 转回 Claude 并交常浩。只调整内部函数或测试方案、不碰这些边界的，不升级 |

下一轮没有新价值、又不满足通过时，ChatGPT 应选证据不足暂停或决策升级，不选返修。

### 5.4 计轮与两种计数

- **计一轮**：ChatGPT 做了一次实质审核（回信给出四档出口之一），包括证据不足暂停。
- **不计轮**：送审前材料不齐被驿窗拦下；没送到、也没有回信；只请 ChatGPT 补格式。没确认送到、但回信到了的，照算一轮（见第 4 节「送达未确认」）。
- **授权周期轮数**：从第一次送审或常浩最近一次介入（插话、授权续审）起算，常浩介入后从 1 重计。上限按它判断。
- **审查链总轮数**：按任务（同一验收目标）认，**永不重置**：换 head SHA、换会话、换 PR、拆单、换工单编号都接着算；台账同样永不清空。总轮数用于展示、运行记录和价值评估。
- **审查链身份**：同一验收目标有一个稳定的审查链标识，第一次送审时生成；PR、会话、工单都只是挂在它下面的交付对象。跨 PR 续审时，送审包写明审查链标识、原验收目标、已累计轮数和未关闭台账。驿窗不判断两个 PR 在语义上是不是同一任务：填了 `chain` 就核对这个标识有没有记录，没有就拒收，不当成全新的审查链从第 1 轮开始；累计轮数和台账由驿窗按自己的记录往下接，送审包里写的数字只作说明。不填 `chain` 时，按同一 PR 最近一张未通过的接力继承；同一 PR 通过后再送，开新链。是否属于同一验收目标拿不准时，按同一条链续审。
- **信任边界**：换一个会话、又换一个工作目录、不填 `chain`、不写同一个 PR，驿窗认不出是同一个验收目标，按新目标处理，不宣称机械防住了这种拆单；驿窗记录只保留有限张数的接力（张数见驿窗通道文档），链上最后一张被挤掉后再填这个 `chain` 会被拒收。

### 5.5 上限与机械控制（驿窗执行；工程审查与思维评审共用）

- **上限**：本次授权周期最多 N 轮，N 取驿窗设置「审核轮数上限」：驿窗出厂默认 5，可在 1–9 之间调（常浩 2026-11-14「最高走审核 5 轮」；2026-11-19 改为可调到 9、默认仍 5，postpane#409）；常浩 2026-11-28 定本机设为 **3**（`chatgpt/config.json` 的 `reviewLimit`，问答框选「压到 3 轮」），工程审查与思维评审共用。思维评审到顶后再送同样拒收。
- **最后一轮预警**：离上限还差一轮、而且出口是还可能继续的非终局状态（返修、证据不足暂停），转回时提示「下一轮是最后一轮」。决策升级已交常浩，不另外预警。
- **到顶**（驿窗界面上叫「停」）：到上限那一轮的出口是返修或证据不足暂停，驿窗停下，发专门的到顶提示，卡上列各轮回顾（接力卡时间线逐轮列出每封回信的意见和结论；常浩 2026-11-19 定不另统计每轮新增与关闭的问题数，postpane#409），请常浩介入确认去向（第 6 节）。那一轮是通过就照常结束并通知常浩；是决策升级，照决策升级交常浩。
- **通过通知**：任何一轮通过（没到上限也一样）都通知常浩。
- **版本锚点、送达未确认、格式补一次**：见第 4 节。
- **到顶后续审与新开**：常浩授权继续时，调用填 `extra`，写明谁授权、为什么、目标，并记进运行记录（第 7 节）；驿窗开一个新授权周期，从 1 重计，审查链总轮数不变。`extra` 不是 Claude 自己说了算（常浩 2026-11-14 定的口径）：驿窗读发起会话当前这一轮是谁开的头，必须在这条链最近一次转回之后、由外面的话开头才认——常浩在会话里打的字，或经驿窗插件进来的话（侧栏回复、智能体互发消息，带不带「以我的身份」都算），但不能是任何一张接力转回的原话；读不到或是 Claude 自己接着跑的这一轮，就拒收。这是信任边界：常浩打开「以我的身份发送」就是授权智能体替他说话。同一会话或同一工作目录里有一张到顶、还没了结的接力时（工程审查和思维评审各算各的），新开同类送审也要照这个口径核实这一轮由外部消息开头（但不用填 `extra`）；常浩在侧栏结束那张，或开口后新开的那一张，才算了结，等常浩处理 24 小时没动静被驿窗自动结束的不算。
- **思维评审怎么套用**：上面的上限、两种计数、格式补一次、通过通知、到顶后续审与新开，思维评审照样适用，只是把「返修」换成「继续深化」：到上限那一轮仍是继续深化或证据不足暂停就停下交回常浩，任何一轮评审收口都通知常浩。这是工具层的安全上限，不是认知结论；思维评审不套用问题台账和 P0/P1，出口、末两行和什么时候收口按 thinking-review。
