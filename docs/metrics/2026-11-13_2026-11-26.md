## 数一 人工介入负担

### 口径

- **一次介入**：常浩亲手发的一条消息，满足其一：①上一轮 AI 停下来问了他（`wrap_up` 带了问题或按钮，或调了 `AskUserQuestion`）；②是一句放行短话（≤ 20 字，如「继续」「合并」「按推荐开工」）。
- **按独立事件算**：AI 停下来之后、下一次再停之前，常浩发的几条消息只算一次。
- **必要**：AI 停下来问的事属于这几类：花钱、对外发送或发布上线、删除、装机或重启、改已定内容（含改全局指令、LESSONS、钩子、登记表）、超出授权或重大又没有安全默认（新功能、选方向、三版选一），以及只有常浩能做的操作（刷新插件、实机跑清单、授权全屏控制）。按 AI 的提问和按钮文字用关键词归类。
- **不必要**：不属于上面几类，常浩回的是 AI 的推荐按钮或一句放行；AI 没问、常浩自己回「继续」也算。
- **单列三栏**：交接启动（点交接卡「开始」「你自己启动」：「卡由常浩点」是已定内容，本期不算不必要）；常浩给了推荐以外的回答（选了非推荐按钮、改要求、追问，算他做了判断）；重复手工（「Try again」重试、同一段话贴进多个会话）。
- **归一化**：每 100 个「有常浩亲手消息的会话」。前后半窗分别按各自的会话数归一化；有的会话两边都有，所以前后会话数相加大于全窗。
- **本期读法**（数值见本机文件）：不必要明显多于必要，而且不必要里绝大多数就是 AI 的推荐按钮；后 5 天每天的不必要次数比前 9 天明显少，和两条规则生效对得上，但后 5 天会话也少，不能全归功于规则。

### 抽样核对（两轮，每轮每栏 10 条）

- 第 1 轮：必要判对 7/10，不必要判对 6/10。误判：「归档会话」被算成删除（归档能撤回）；app 代码里的「panic 钩子」被当成规则钩子；「刷新插件」「在电脑前跑清单」这类只有常浩能做的操作被算成不必要；改登记表状态、批复盘提案没认出是改已定。按这些改了关键词，加了「亲手操作」类。
- 第 2 轮（换随机种子重抽）：必要判对 9/10，不必要判对 8/10。剩下的误判是「交接卡由你点还是我启动」和「要不要用全屏控制」：前者单列为交接启动，后者按全局第 11 节要常浩点头，改算必要。
- 另抽 10 条「推荐以外的回答」：都是常浩做了实际判断，归类成立。
- 误差估计：按第 2 轮，必要和不必要各有约 10%～20% 的条目放错栏，两个方向都有，两栏的量级关系不受影响。

### 局限

- 点按钮和手打在记录里分不出来，「等于推荐」只是文字一致。
- 必要 / 不必要按 AI 的提问文字归类，AI 问得含糊（「接下来怎么办？」）时容易放错栏。
- 「常浩给了推荐以外的回答」里混着纠正和新需求，没再细分。
- 转达、复制粘贴到别的应用这类操作，会话记录里看不到，重复手工没数全。
- Codex 本期没有常浩亲手的消息，数一只覆盖 Claude。

## 数二 有效交付

### 口径

| 项 | 怎么取 |
|---|---|
| 合并的 PR | `gh search prs --owner Natsukashii1997 --merged-at 2026-11-13T00:00+08:00..2026-11-26T23:59+08:00`；去掉只改交接 / 登记的（标题以 CURRENT、记录、交接、登记开头） |
| 其中 14 天内被撤回 | 各仓库 main `git log --grep` 找 revert，加 `gh search prs revert`；故意的撤回演练（如合并放权的撤回演练）不算 |
| 关掉的 issue（完成） | `gh search issues --closed …`，`reason:"not planned"` 单独查后扣掉 |
| 业务产出 | 人工数，见下 |

**撤回的 14 天观察期没满**：窗口最后一天合并的 PR 要到 12-10 才满 14 天。12-10 后按同样的命令复核一次，结果补进本机文件。

**业务产出的口径**：交给常浩以外的人看或用的东西（发出去的通知、汇报、表格、给业务方的原型或文稿）。来源：工作目录在业务目录的会话，加临时目录里做业务的会话；看其中的飞书写入命令和 Artifact 发布，按交付件去重；看不到交出去的、窗口内没被接受的、分不清是业务还是个人规划的，单列「拿不准」。

### 抽样核对（PR 10 个）

随机抽 10 个算进合并数的 PR，逐个用 `gh pr view` 确认是 MERGED，改动 2～40 个文件，都是功能、修复、规则或报告，不是记账。另看了 5 个被剔除的：都是 CURRENT、交接、登记类。发现漏剔：标题不以「登记」开头的登记表补登 PR 算进去了，下期剔除规则要补。

### 局限

- PR 是很小的单位，一个功能常拆成好几个 PR；PR 数和「件」不可比，只适合同口径前后比。
- 本期 PR 主要来自个人 AI 工具链，PR 数主要反映工具链的活，不反映业务交付。
- 合并不等于常浩验收过：大部分 PR 合并前过了 AI 审查或 ChatGPT 审查，常浩本人没逐个看。
- 业务产出靠人工从会话里认，漏数的可能比多数大（没用飞书命令、没发 Artifact 的交付看不到）。

## 数三 重大返工率

### 口径

- 分母「已说完成的任务」：算进数二的合并 PR 加确定的业务产出。
- 分子「实质返工」：
  - PR 层：14 天内被撤回的，加被后来的修复 PR 在标题里指名的。
  - 强纠正层：session-retro 规则初筛出的强纠正，逐条人工判。AI 已经说做完、常浩指出理解错、方案错或质量不行要重做的算；改一处细节的不算；新需求被关键词误中的不算。
- 合审查前的返修（PR 合并前多轮审查改的）不算：那时还没说完成。这一类本身量很大，是另一种成本。
- **本期读法**（数值见本机文件）：返工率是个位数百分比；业务产出的返工远高于工具链。两边单位不一样（件和 PR），不能直接比率对比，但方向清楚：给别人看的东西，返工最多。

### 抽样核对

强纠正全量逐条判（多于 10 条），每条记了项目、判定（理解错 / 方案错 / 质量 / 不算）和一句概括理由，明细在本机文件。

### 局限

- 强纠正只是规则初筛：没命中关键词的纠正（只说「重新做」不带「不对」）漏掉；弱信号没逐条判。真实返工只会更多。
- 「已说完成」没逐条核：每条强纠正前 AI 的上一句都说了做完、发了、改好了，但 PR 是否都「说完成」没核。
- 被修复提交指名只看了 PR 标题；修复提交多数引 issue 号不引 PR 号，这一路几乎抓不到。

## 红线 不可逆操作违规

- 怎么查：①常浩亲手消息里找「谁让你」「擅自」「没问我」「为什么直接……发 / 删 / 装 / 合并」等说法，逐条看上下文；②找常浩只回了「合并」类短话、AI 随后却说装到本机 / 已安装的，逐条看上下文。
- 本期确认违规为零。有几次边界事件（常浩只回了「合并」、AI 连带装机），都发生在 11-22「合并之后装机仍先问」写进《工程流程》之前，当时的规则没明确要另问，所以不计违规。常浩 2026-11-27 定（经复盘主会话转来「全部都按推荐」）：不按现行规则回算，从下一期起按现行规则（合并后装机仍先问）算。明细在本机文件。
- 局限：常浩没发现、没说出来的违规查不到；只扫了「合并后装机」这一种模式，「没问就发群」「没问就删」没有专门扫。

## 哪些能机械取，值得下一步自动化

| 部分 | 能不能机械取 | 建议 |
|---|---|---|
| 数一：常浩亲手消息、独立事件、等于按钮 / 推荐、每 100 会话 | 能。session-retro 0.3.0 已经认得出来源和按钮 | 自动化，进方案第六项第 2 步的 `--metrics` |
| 数一：必要 / 不必要分栏 | 半机械。关键词表两轮抽样后约八到九成判对 | 自动出初值，每期人工抽 10 条核；关键词表跟着规则改 |
| 数一：重复手工 | 部分。重试、长段搬运能取；跨应用的复制粘贴取不到 | 自动取能取的两项，其余不追 |
| 数二：合并 PR、撤回、关掉的 issue | 能（`gh search`） | 自动化；记账类 PR 的剔除规则补「已定内容登记表」这类标题；撤回按「上期的 PR 到本期满 14 天」滚动复核 |
| 数二：业务产出 | 只能出候选（业务目录会话里的飞书写入、Artifact 发布） | 自动列候选，人工去重和判定 |
| 数三：PR 撤回 / 被指名 | 能，但信号弱 | 自动化；补「修复提交引 issue 号、issue 对应的 PR」这一层 |
| 数三：强纠正分类 | 不能 | 留在每期复盘里人工判 |
| 红线 | 能出候选（「只回合并却装机」等模式、常浩的质问说法） | 自动出候选，人工判 |
| 手动切模型 | 能（`/model` 记录减 AI 代切） | 自动化 |

自动化以后，数值同样写在本机，不进本仓库；仓库里只记口径变化。
