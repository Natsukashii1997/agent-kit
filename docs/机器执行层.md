# 机器执行层：权限规则、hook、agent-kit 自检、每周汇总

来由：[2026-11-05 最佳实践对照报告](research/2026-11-05-best-practices.md)的结论是：「写给人和模型读的规矩」已经够严，缺的是「到了关键时刻机器一定会执行」的那一层。这里把 5 件事落成可安装的文件。

报告第 5 节的本机核对发现，第 3 件（体检）、第 4 件（会话复盘）在 my-skills 里已经有同日自建的实现：`automation-checkup`（my-skills#30）、`session-retro`（my-skills#28）。所以这里**不再重复做**它们：
- launchd、Hermes 定时任务、crontab 的体检，归 automation-checkup。
- 会话复盘归 session-retro。
- 本仓库只做它们不覆盖的：agent-kit 自己装进本机的东西装没装好、两份全局指令是否一致、坑提醒的命中统计。

> 术语：
> - **hook**：Claude Code / Codex 在固定时刻（这里是「执行命令或改文件之前」）一定会跑的小脚本，不靠模型自觉。你本机已有的 9 个和 7 个 hook 都不在这个时刻，和这里加的不冲突。
> - **权限规则**：设置文件里的一行，写明哪类命令「直接拒绝」或「先问我」。
> - **状态目录**：本机存提醒日志、自检报告的地方。macOS 上是 `~/Library/Application Support/agent-kit/`，不放 `/tmp`（G-01）。

## 一次装好（在本机终端里，约 5 分钟）

**装之前**：
- 关掉正在跑的 Claude Code / Codex 会话，免得它们同时改设置文件。
- 终端进到 agent-kit **主目录**（不是 worktree），运行 `git status`：第一行应是 `On branch main`，并且已经拉到最新、没有冲突。
  - 不在 main 上时，安装脚本会拒绝写入。原因是 hook 会在所有会话的每条命令前运行，只能装审过、合并过的版本。

**先预览**，只列出要改什么，不写任何文件：

```bash
node tools/install.mjs --only claude
```

核对预览里写的是「deny 新增 16 条、去掉 0 条，ask 新增 0 条、去掉 0 条」，并且 hook 一共放入 11 组：PreToolUse 4 组、PostToolUse 2 组、UserPromptSubmit 3 组、SessionStart 1 组、Stop 1 组，另有两行分别说明首轮整理、上下文提醒的配置是「已在」「从旧位置迁移」还是「拷示例」（上下文提醒还会写拷过来几条旧提醒记录）。以前装过、带着 23 条 ask 的，重装时预览会写「ask 去掉 23 条」（#27）。没问题再装：

```bash
node tools/install.mjs --only claude --apply
```

**装完验收**：
1. 新开一个 Claude 会话，用 `/hooks` 确认原来的 hook 都在，另外多了 agent-kit 的 11 组；`~/.claude/hooks/session-organize-once/` 下旧的首轮整理条目、`~/.claude/hooks/context-handoff/` 下旧的上下文提醒条目，都已换成状态目录 `runtime/` 里的副本。
2. 让 Claude 建一个**临时仓库**，`origin` 指向本机的一个空仓库（不要在真实仓库里试强推），然后依次试：
   - `git push --force origin main`：应该被拒绝；
   - `git push origin main`：应该不问、直接推（#27 起 Claude 侧不再先问）；
   - `git push -u origin claude/test`：应该不问、直接推。
3. 跑一遍自检，应该全是 ✓：
   ```bash
   node tools/doctor.mjs
   ```
4. 预览一次卸载，确认能卸（不加 `--apply` 就不会真卸）：
   ```bash
   node tools/install.mjs --uninstall
   ```

**Codex 一侧**：Claude 那边跑顺后再装，命令是 `node tools/install.mjs --only codex --apply`。装完先在终端里运行下面这条，应该输出 `forbidden`；然后在 Codex 里按第 2 步的临时仓库再试一遍：

```bash
codex execpolicy check --rules ~/.codex/rules/agent-kit.rules git push -f origin main
```

**会改什么、怎么恢复**：
- 会改的文件：
  - `~/.claude/settings.json`：加 `permissions.deny` 和 11 组 hook（以前装进去的 `permissions.ask` 规则会去掉）：
    - PreToolUse：guard-git、lessons-remind、thinking-review-nudge、bash-precheck；
    - PostToolUse：skill-usage、上下文提醒；
    - UserPromptSubmit：thinking-review-nudge、首轮整理、上下文提醒；
    - SessionStart：首轮整理（matcher `startup|fork`）；
    - Stop：wrapup-guard（收尾按钮框兜底，#150）。
  - `~/.codex/hooks.json`：加 2 个 hook。
  - `~/.codex/rules/agent-kit.rules`：新建。
- 不碰 `config.toml`，也不碰凭据文件。你原有的设置和 hook（PostPane 通知等）原样保留，和 agent-kit 的 hook 在同一组里也不动；只有 `~/.claude/hooks/session-organize-once/` 下的旧首轮整理条目、`~/.claude/hooks/context-handoff/` 下的旧上下文提醒条目会被认出来、换成 runtime 副本。
- 设置文件会被重排成 2 空格缩进，内容不变。
- 状态目录（`~/Library/Application Support/agent-kit/`）里的东西：
  - `backups/<时间>/`：每次写之前，先把原文件备份到这里，不留在 `~/.claude`、`~/.codex` 里。
  - `runtime/`：hook 脚本和 LESSONS.md 的副本，设置里指向它。所以主目录换分支、停在冲突里、worktree 被删，都不影响已装的 hook。代价是仓库里改了 hooks/ 或 LESSONS.md（比如加了新坑的「触发」行），要在 main 上**重跑一次 `--apply`** 才生效；`doctor` 会提示副本落后。
  - `session-organize-once/`：首轮整理钩子的 `config.json`（真实配置：侧栏分区 ID、项目路径，不进仓库）和 `state/`（运行记录、`decisions.log`）。安装时已有配置就不动；没有就从旧位置 `~/.claude/hooks/session-organize-once/config.json` 拷过来，再没有就拷仓库里的示例 [config/session-organize-once.example.json](../config/session-organize-once.example.json)，要按本机改。卸载不删这个目录。
  - `context-handoff/`：上下文提醒钩子（#105，上下文到 50%、70% 时提醒提交接卡）的 `config.json`（窗口大小和阈值）和 `state/`（每个会话已提醒过哪些阈值）。安装时已有配置就不动；没有就从旧位置 `~/.claude/hooks/context-handoff/config.json` 拷过来，再没有就拷示例 [config/context-handoff.example.json](../config/context-handoff.example.json)；旧位置 `state/` 里的提醒记录一并拷过来（同名不覆盖），已提醒过的会话不会再提醒一次。旧目录不删。卸载不删这个目录，但会把这个 hook 从设置里去掉。
  - `install-manifest.json`：记下这次新加了哪些权限规则。卸载 `node tools/install.mjs --uninstall --apply` 只删这些；你自己原来就有的同名规则不动。
- 装之前的自检只测脚本本身。写进设置的那条命令能不能跑起来，由 `doctor` 测。

## 第 1 件：不可逆操作，机器把关

| 操作 | Claude Code | Codex |
|---|---|---|
| 强推到 main/master（含 `--force-with-lease`、`+main`），或删除远端 main/master | **直接拒绝**：权限规则 deny，加 hook 兜底 | **直接拒绝**：执行策略 forbidden，加 hook 兜底 |
| `gh pr merge`、`gh api …/merge`、GitHub MCP 的合并工具 | 放行 | 只有 `gh pr merge` 会问 |
| 推 main/master（`git push origin main`、`git push -u origin main`） | 放行 | 先问你 |
| **当前就在 main 上**，执行不写分支名的 `git push`，或写 `HEAD` 的 `git push origin HEAD` | 放行 | **不管**（Codex 的 hook 不支持「先问」） |
| 强推分支（`-f` / `--force`） | 放行 | 先问你，`--force` 写在前面时才问到 |
| 删除远端分支、`git reset --hard`、`git clean`、`git branch -D`、`git stash drop/clear` | 放行 | 先问你 |
| `--force-with-lease` 推自己的分支 | 放行（《工程流程》第 5 节第 3 步允许） | 放行 |
| 推的不是 main/master 的 `git push`、`gh pr create`，要推的分支带着本地 main 上还没推到 `origin/main` 的提交（#76） | **直接拒绝**：hook | **直接拒绝**：hook |
| 跳过仓库钩子：`git push --no-verify`、`git commit --no-verify` / `-n`（复盘 P6，2026-11-20） | **直接拒绝**：hook | **直接拒绝**：hook |

Claude 一列的「放行」是常浩 2026-11-07 的决定（#27）：Claude 会话默认 bypass，这类代码层面的审批他看不出潜在后果、实际总是直接通过，弹窗只增加打断，所以只保留「直接拒绝」这一层，其余交给 Claude 判断。放行只是不弹权限窗；《工程流程》第 5 节的合并规则（能按策略合的交 Hermes 合并，例外等常浩说合并）等书面流程照旧。Codex 一列未改。

- **推送前检查（#76）**：2026-10-27 digital-twin 从本地 main 拉 PR 分支，把别的会话 3 个没推的提交（含受限内容）一起推上了 GitHub，只能删远端重建。[hooks/guard-git.mjs](../hooks/guard-git.mjs) 现在在 `git push`（推的不是 main/master）和 `gh pr create` 之前，看本地 main（没有 main 时看 master）比 `origin/main` 多出的提交有没有被要推的分支带着，带着就拒绝，理由里列出这些提交（最多 5 个）和两种正确做法：从 `origin/main` 重新拉分支再 cherry-pick；或把标题列给常浩、他回“推”后先推 main（《工程流程》第 5 节第 1 步）。
  - 只看本机已有的引用，不 fetch（hook 要快，也不该在命令前联网）。
  - 不拦：推 main/master 本身（归《工程流程》5.1）、`--all` / `--mirror` / `--tags`、删除远端分支、分离头指针、没有远端或没有 `origin/main`、不在仓库里、git 出错。
  - 认得 `git -C 目录`、参数乱序、`cd 目录 && git push`（#76 起 `cd` 到真实存在的目录后，后面几段按那个目录判断，强推规则看当前分支时也一样；解析不出真实目录时照旧用会话目录）、`gh pr create --head`。
  - 样本：`tests/guard-git.test.mjs` 用临时仓库摆出 10-27 的形态（本地 main 领先 3 个，从它拉分支再推）证明会拦，另有不该拦的反例；`tools/doctor.mjs` 实跑同一个形态。已装的还是旧副本时，自检只给 ⚠ 提示重装。
- **为什么拒绝用两层**：官方文档说 hook 出错时默认放行，所以硬红线以权限规则为准。但权限规则只认固定写法，下面这些写法认不出来，交给 hook [hooks/guard-git.mjs](../hooks/guard-git.mjs) 兜住：
  - `git -C 目录 push`；
  - `env X=1 git push`、`bash -c "…"`；
  - 参数顺序打乱。
- 规则文件：
  - Claude：[config/claude-permissions.json](../config/claude-permissions.json)，只有 deny（ask 已清空，#27）。官方文档写明 deny 在任何模式下都生效，包括 bypass。
  - Codex：[config/codex/agent-kit.rules](../config/codex/agent-kit.rules)。
- 已核实：
  - **Codex 规则**：用 Codex 0.166.0 的 `codex execpolicy check` 实测了十几个命令。本机装了 codex 时，`tests/codex-rules.test.mjs` 会自动复测。
  - **Codex hook**：以下几点是读 `openai/codex` 源码确认的，没在真的 Codex 里跑过，第一次可能要你确认信任：
    - `~/.codex/hooks.json` 和 Claude 同格式，hook 默认开启；
    - PreToolUse 认 `permissionDecision: "deny"` 和 `additionalContext`，不认 `ask`；
    - shell 工具在 hook 里叫 `Bash`，改文件工具叫 `apply_patch`，`Edit`、`Write` 也能匹配到它；
    - 支持 `timeout` 字段；
    - 只加载 `~/.codex/rules/` 下扩展名为 `.rules` 的文件。
  - **guard-git**：有三十多个命令样例的测试。
- 没核实：没在真的 Claude Code 里实装跑过（云端会话改不到你本机的设置）。Claude 的 deny / ask 规则是照官方文档写的，所以装完一定要按上面的验收步骤试一遍。
- 已知漏洞：
  - Codex 的规则只认开头几个词，`git push origin feature --force` 这种把 `--force` 写在最后的不会问。
  - Codex 里，当前在 main 上执行不写分支名的 `git push` 不会问；用 `gh api` 或 MCP 合并 PR 也不会问。
  - `git -C 其他目录 push origin main`（不带强推）两边都不会问；带强推照样被拒绝。
  - 只看真正执行的命令（2026-11-20 起）：引号里的文字（提交说明、PR 正文、`echo "…"`）和 heredoc 正文不当命令，里面写着 `git push -f origin main` 不拦；heredoc 喂给 shell 的（`cat <<EOF | bash`、`bash <<EOF`）照样判断。`$( … )` 命令替换里的命令不单独判断（`echo "$(git push -f origin main)"` 拦不住，和以前一样）。引号里的多行文字恰好含 `<<词` 时，会把后面几行误当 heredoc 正文跳过。
  - `cd` 的目标含变量或命令替换（`cd "$DIR"`、`cd $(…)`）、是 `cd -`、或目录不存在时，hook 不知道会进哪个目录，后面几段照旧按会话目录判断（不会因此放松强推 main 的拦截，但推送前检查可能查错仓库或查不到）。
  - 推送前检查只比本地引用：别的会话往 `origin/main` 推过、本机没 fetch 时，判断按本机看到的 `origin/main`。
  - **Hermes 不受这套约束**：它的派单靠什么兜底，要你另外定。
- 关于本机已装的 `git-guardrails-claude-code` skill：它是 Matt Pocock 用来「设置拦危险 git 命令的 hook」的技能。按我对它的了解，它会把 `git push` 整个拦掉，而各会话推分支开 PR 是日常操作，所以建议不要再用它装一份。我没读你本机那一版，这一点要核对。

## 第 2 件：LESSONS 按关键词提醒

- LESSONS 每条 G-xx 末尾新加了一行「触发：」，写的是碰到这条坑时命令或代码里会出现的词。
- hook [hooks/lessons-remind.mjs](../hooks/lessons-remind.mjs) 在执行命令、改文件之前比对这些词，命中就把那条坑的标题和「正确做法」的第一句提示给模型。例如命令里有 `launchctl bootstrap` 时会提示 G-18，写 `LaunchAgents` 下的 plist 时会提示 G-05。
- 触发行可以限定场合（瘦身提案，2026-11-20 常浩批）：「触发（改文件）」只在写文件时比对（Claude 的 Write、Edit、MultiEdit、NotebookEdit，Codex 的 apply_patch、Edit、Write），「触发（主目录）」在 worktree 目录（路径里有 `/worktrees/`）里不比对；改的全是 `.md` 文档时一律不比对。
- 它只提醒、从不拦截；同一会话里同一条只提醒一次。
- 每次命中都记一行到状态目录的 `lessons-hits.jsonl`，记时间、会话、工具名、所在目录、命中的编号（`ids`）、真正提醒了的编号（`reminded`，同一会话同一条只提醒一次）和命中的触发词（`words`，2026-11-20 起），不记命令内容。doctor 的「近 7 天坑提醒」分开写提醒次数和匹配次数。这是 automation-checkup 和 session-retro 都没有的数据：哪条坑在实际工作中被碰到几次、在哪些项目。
- 「触发」词怎么写，见 LESSONS 开头「怎么写」。词太宽会天天误报，这时就收窄。G-09（界面改动）想不出可靠的词，写了「无」。
- 改了「触发」行要在 main 上重装才生效，见「一次装好」。

## 第 3 件：本机体检 = automation-checkup（my-skills#30）+ agent-kit 自检

- **launchd、Hermes 定时任务、crontab**：用 my-skills 的 automation-checkup。合并 my-skills#30，按需定时跑。
- **agent-kit 自检**：
  ```bash
  node tools/doctor.mjs
  ```
  不用配置就会查：
  - Claude 的拒绝规则和 7 个 hook（含首轮整理，启动和发消息两处都要指向 runtime 副本；含上下文提醒，发消息和工具调用后两处都要指向 runtime 副本；状态目录里要有这两个的配置）、Codex 的拒绝 / 先问规则和 2 个 hook 装没装；已装的副本（`.mjs`、`.py`）和仓库是否一致。
  - 已装的 hook 能不能**按设置里写的那条命令**真的跑起来（guard-git 实跑两样：强推 main；在临时仓库里摆出 10-27 的形态推分支，#76）。hook 坏了默认放行，平时看不出来；比如 Homebrew 升级 node 后路径变了，这一步会报 ✗。
  - 两份全局指令里「跨项目沉淀」那一节是否逐字一致（第 5 件）。
  - Claude 自动记忆开没开。
  - 近 7 天哪些坑被提醒过。
  - 项目目录（默认 `~/Documents/ChatGPT/个人/work`，`doctor.json` 的 `workRoot` 或 `AGENT_KIT_WORK_ROOT` 可改）下带 `scripts/hooks/pre-push` 的仓库，本机有没有装 `core.hooksPath=scripts/hooks`；没装的报 ⚠ 并给安装命令（复盘 P6，2026-11-20）。只读，不替你装：钩子出问题时会有意停用，这时的 ⚠ 可以忽略。
  - 同一个项目目录下，各仓库的主目录落后远端 main 几个提交（「合并了没拉」，#163）。从主目录运行的仓库（skill 链接、常驻任务）落后，就是合并了没生效。不联网，按上次 fetch 的远端引用算；只列出来（·），不算警告，也不替你拉；有仓库查不了时也只给 ·，全部查到且都不落后才给 ✓；`doctor.mjs --json` 的 `results` 里相应多一项；拉不拉按《工程流程》第 5 节。驿窗二进制、Chrome 插件、Hermes 脚本这类「运行版本和主干版本」的比对不在这里，归各自项目的体检。
- 可选配置：复制 [tools/doctor.example.json](../tools/doctor.example.json) 到 `~/Library/Application Support/agent-kit/doctor.json`，填上 `repos`，就会顺带查各仓库本地 main 有没有别的会话留下的、没推的提交（《工程流程》5.1）。
- 报告存在状态目录的 `doctor/` 下：第一行是开始时间，最后一行是 `exit N`（G-12 的写法），最多保留 60 份。有 ✗ 时退出码为 1。
- 要不要定时跑：可以并进 automation-checkup 的定时任务里一起跑。不要单独用 launchd 跑：agent-kit 放在「文稿」目录下，launchd 直接启动的程序读不了「文稿」（G-05）。

## 第 4 件：会话复盘 = session-retro（my-skills#28）+ 每周汇总

- 会话复盘用 my-skills 的 session-retro：纯本地、只出提案、片段脱敏。报告原来建议的第三方工具 sheal 不用了。
- 每周整理时再跑：
  ```bash
  node tools/weekly-review.mjs
  ```
  它把 agent-kit 自检结果、近 7 天坑提醒统计（按条写提醒次数、会话数、关键词匹配次数和项目，和 doctor 同口径）、再犯和等批的提升（见下面「再犯统计」）汇成一份 Markdown，存到状态目录的 `weekly/<日期>.md`，并打印文件路径。不带调度，什么时候跑由每周整理的人定；要定时另开 issue 由常浩确认。

## Bash 预检：防会话卡在没人点的安全检查批准上（#49）

**来由**：2026-11-09 一天里 Claude 桌面版 6 次弹「Claude Code stopped responding」，都是同一条链：
1. Claude 写的 Bash 触发了 Claude Code 内置的「危险 rm」安全检查，这个检查在 bypass 模式下也要求人工批准；
2. 本机的批准请求被驿窗的 PermissionRequest 钩子接走，Claude 窗口里不弹；
3. 驿窗「等待回答」设成一直等，没人点；
4. 约 16 分钟没动静（`main.log` 里 `timed out after 960~1016s of inactivity … last_tool_name=Bash`），桌面版判会话停止响应。

`hooks/bash-precheck.mjs`（只装 Claude，matcher `Bash`）在执行前认出这几类写法，当场拒绝并告诉 Claude 怎么改写：

| 类别 | 写法 | 改写 |
|---|---|---|
| `rm-var-glob` | rm 目标里既有变量又有通配符：`rm -f "$O"/*.zip`、`rm -f $L/*.log` | 变量写成 `"${O:?}"`（变量为空时 shell 直接报错、不去删） |
| `rm-whole-dir` | 整目录通配：`rm -rf shots/*`、`rm -rf "$TMPDIR/ck/"*` | 收窄到文件类型（`shots/*.png`）或写明文件名；要清空整个目录就按字面路径删目录再重建 |
| `rm-unset-var` | rm 目标里的变量在这条命令里没赋值、环境里也没有 | `"${X:?}"`，或在同一条命令里先赋值 |
| `rm-substitution` | rm 目标里有 `$( )` 或反引号 | 先存进变量并检查不为空，再用 `"${X:?}"` |
| `parse-dollar-dollar` | 命令里有 `$$(`（heredoc 里嵌的前端代码），`p.$$(` 不算 | 代码先用 Write 写成文件，再执行 |
| `parse-escaped-subst` | 命令里有 `\\$(`（两个反斜杠后的 `$(` 会真的开启命令替换） | 放进单引号，或写成文件 |
| `kill-pkill-broad` | 宽泛的 `pkill -f`：模式里没有路径、4 位以上数字、带扩展名的文件名，如 `pkill -f 'pnpm test'`（全局坑 G-32，2026-11-19；不是防卡住，是防杀掉别的会话的进程） | 用任务 ID 停（TaskStop、`$!`）；或模式写到本 worktree 绝对路径、自己的端口、脚本文件名；或先 `pgrep -fl` 看清再 `kill <PID>` |
| `env-ps-environment` | `ps` 带显示环境变量的选项：带横线的只认大写 `E`（`-E`、`-Eww`、`-axE`），不带横线的只认第一个参数里有 `e` / `E`（`e`、`eww`、`auxe`）。macOS 带横线的 `-e` 是「所有进程」，不拦（全局坑 G-42，2026-11-19；不是防卡住，是防登录令牌明文进会话记录） | 想知道进程是谁用 `ps -o pid,ppid,command`；只要变量名用 `env \| cut -d= -f1`（当前 shell）或看启动配置；只想知道有没有、对不对用 `[ -n "${X:-}" ]` 或比 `shasum` 摘要，不打印值 |
| `env-proc-environ` | 读 `/proc/<pid>/environ` 的命令（`cat`、`xargs`、重定向）；`echo`、`printf`、`git`、`gh` 里只是提到的不算（G-42） | 同上 |

- **只会更早拒绝，从不替检查放行**：放行的命令照样经过 Claude Code 自己的检查。拒绝说明里写明「改写后删的范围不能变大」。
- **规则从哪来**：近 14 天会话记录里 66280 条 Bash，30 条被这个检查拦、11 条卡到会话断开；对照 Claude Code 2.1.317 的检查代码（tree-sitter 解析出错就要批准；rm 目标里的变量「可能为空」也要批准）。同样的 rm 写法，前面有 `cd` 到工作目录外、或有 `source` 时才会被拦，钩子不分上下文一律拦：漏拦一次是卡 16 分钟，误拦一次只是改写一下。
- **量过的效果**（同一份语料）：30 条被检查拦下的命令拦住 29 条；漏的 1 条是 heredoc 里的写法，原因没认出来。正常命令误拦 94 / 66240（0.14%），多数是本来能过的 `$OUT/*.png`，改成 `"${OUT:?}"/*.png` 就行。
- **实测过**：
  - 用桌面版自带的 Claude Code 2.1.317，在 bypass、不挂任何钩子时跑了 26 条探针：钩子要拦的写法真的会被检查拦下；钩子建议的改写写法全部直接能跑。这两组写进了 `tests/bash-precheck.test.mjs`，当天 6 条原命令放在 `tests/fixtures/`。

- `kill-pkill-broad` 的口径（2026-11-19）：近 14 天 95583 条真实 Bash 里 `pkill -f` 有 320 条，多数是按端口或脚本名精确重启自己的开发服务；全拦误伤太大，只拦没有锚点的 76 条（驿窗 L-33、L-37 的原命令在内）。这一类和 `env-` 两类的拒绝说明单独写，不提「危险 rm」。

  - 覆盖不到：Codex；藏在 `bash -c '…'`、`docker exec`、`python -c` 引号里的命令（近 14 天有 2 条读容器里 `/proc/<pid>/environ` 的没拦到）；`env`、`printenv`、`set` 打印当前 shell 自己的环境变量（本机 Claude 的 Bash 环境里也有令牌类变量）；`launchctl print`、`launchctl getenv`；程序自己读别的进程环境（`sysctl` 的 `KERN_PROCARGS2`）。

## 收尾按钮框兜底：wrapup-guard（#150）

全局第 12 节「按钮框」要求：收尾要常浩拍板或回话的，`wrap_up` 必须带 `ask` 和 `actions`，常浩在桌面应用和驿窗侧栏点一下就能答。2026-11-27 取证：近 14 天〔等你决定〕1759 次只有约 67% 带按钮框，〔等你操作〕792 次只有约 23%；一条命令都没跑的轮（转话、子会话回报）带 `wrap_up` 的只有约 10% 和 2%（2026-11-28 修统计去重后更正：原报 53%、20%、17%、6%，统计和钩子用了同一个错的去重，见下面「去重」；#158）。规则文字已写过「指到他该回复的那句话」，执行率仍远不到全部，零工具轮几乎都漏，所以配钩子兜底。证据在状态目录 `evidence/2026-11-27-wrapup-buttons/`（更正后的统计和回放在 `evidence/2026-11-28-wrapup-dedupe/`），提案页 https://claude.ai/artifact/LFGkWhhynVshBSGkg1B73n 。

`hooks/wrapup-guard.mjs`（只装 Claude，Stop）整份读会话记录（不截断），取本轮最后一条助手消息（Stop 输入的 `last_assistant_message` 优先），只看其中最后一个合法的「**当前状态**：〔…〕」（五个状态词之一，正文里引用的不算）：
- 收尾是〔等你决定〕，或〔等你操作〕〔受阻〕且「下一步」里写了「回复『X』」（也认「回复我」，「回」后面带量词的「回我一句 / 一个 / 一下 / 一条 / 一声 / 一段」「回个」「回一句话」，带冒号的「回我一句：『X』」，带括号举例的「回（比如『X』）」「回复（可以写『X』）」，「回到这里说一声『X』」「回来说『X』」；「回它」「回信」「回到」「回协调会话」这类不是在本会话回话的不认）（否定要直接管着这个「回」才不算：否定词和「回」之间只许隔「你」「再」和一个「在……」地点状语，例如「不要再回复」「无需你回复」「不要在这个会话回复」；「别忘了回复」「分别回复」「不是不要回复」都算要回话；只看「回」所在小句；不限长度。14 天 2361 条写了回话的「下一步」里，没有一条被判成否定），本轮却没有合格且调用成功的 `mcp__ccd_turn__wrap_up`（`ask` 非空、`actions` 1–2 个、每个都有按钮文字或应用动作，工具结果不是错误），就返回 `decision: block`，让模型补调 `wrap_up`、再把收尾三项原样重发（收尾三项仍是最后一条消息，驿窗照常读）。
